We compare various scenarios and see how Flame and 3DE4 handle them.

Input images img_a.exr and img_b.exr are distorted. The task in Flame is to undistort them propertly.
The input images are equipped with a green box which marks the display window
and an orange which marks the data window. Not the in img the two boxes coincide.

img_a:
- data window 2400x1200, display window 2000x1000
- Flame's ReadFile node sets image size to 2000x1000 (good)

img_b:
- data window 2400x1200, display window 2400x1200


In all three scenarios the idea is that the footage is already
large enough to contain the overscan for compositing, therefore
we do not add any additional margin when exporting to Flame.
Both images are created in a way as if the camera filmback
corresponded to an area of 2000x1000, so in 3DE4 we make sure
the Field of View is set to this size.

Pipeline a1:
- In 3DE4 import img_a Data Window
- Set LD to the values used for creating the image.
- Extract FOV from img_a Display Window (by script)
- Export LD to Flame, Oversize 0,0, batch_a_data_window
- In Flame: Import img_a.exr
  * Import Settings -> Image -> Data Window(!)
- Result: out_flame_img_a1_undistort.001.exr, numerically correct but:
  * Display Window = Data Window (maybe not what we want to have)

Pipeline a2:
- In 3DE4 import img_a Display Window
- Set LD to the values used for creating the image.
- Leave FOV at default values
- Export LD to Flame, Oversize 200,100, batch_a_display_window
- In Flame: Import img_a.exr
  * Import Settings -> Image -> Data Window(!)
- Result: out_flame_img_a2_undistort.001.exr, numerically correct but:
  * Display Window = Data Window (maybe not what we want to have)

Pipeline b:
- In 3DE4 import img_b (Data = Display, irrelevant)
- Set LD to the values used for creating the image.
- Set FOV by hand to 2000x1000 at 200,100.
- Export LD to Flame, Oversize 0,0, batch_b_data_eq_display
- Result: out_flame_img_a2_undistort.001.exr, correct
  * Display Window = Data Window as expected

Pipeline b with STMap
- In Flame
  * undistort-node -> Modes -> Render mode -> stmap
  * feed into Flames UVWarp32
- Result: very similar to original Pipeline b
  The bottom line is: The undistort/redistort-batch
  exported by 3DE4 is compatible to Flames UVWarp32.
  It is not clear whether or not the EWA filter is optimal
  for using UVWarp32 for distortion removal -> Research to do.

Output images of Flame have dropped the Display Window, so that
in all outputs we have Data = Display. We may overlook some setting,
but this is way it's not good.
